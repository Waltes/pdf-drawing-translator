# 定制版怎么打包、怎么跟更新

给维护者看的。客户看的是《使用说明_DYNAMIC定制版.md》。

## 一句话

通用版和定制版是**同一套代码**，差别收在 `editions/<id>.json` 里。不 fork 代码。

为什么不分叉：一旦分成两份，通用版修一次 bug 就得去定制版再改一遍，改漏就是客户那边
出问题。这种分叉最后一定会烂掉 —— 两边越走越远，谁也不敢动。

## 目录

```
editions/
  standard.json    通用版配置
  dynamic.json     DYNAMIC 定制版配置
edition.json       当前生效的那份（打包脚本临时改写它，打完还原）
core/edition.py    只负责读配置，不判断对错
data/glossary_dynamic.csv   客户锁定词表
packaging/build_edition.py  打包脚本
```

`edition.json` 被版本控制跟踪，但**不要手改它来做定制版** —— 下次打包会被覆盖，
改的东西悄悄没了。改 `editions/` 下对应那份。

## 打一个包

```bash
python packaging/build_edition.py dynamic     # 定制版：exe + 安装包
python packaging/build_edition.py standard    # 通用版
python packaging/build_edition.py dynamic --no-installer   # 只要 exe，调界面用
python packaging/build_edition.py --defs-only              # 只生成两份中间文件
```

产物：

- `dist/PDF翻译工具DYNAMIC定制版/` —— exe 和运行时依赖
- `packaging/output/PDFTranslatorDynamic_Setup_1.0.0.exe` —— 安装包

脚本中途被打断（Ctrl+C、PyInstaller 报错）也会还原 `edition.json`，用的是 try/finally，
不是「成功后才还原」。这一点很重要：如果还原漏了，下一次打包会悄悄带上上一次的发行配置，
打出来的包名字是错的，而且没有任何提示。

**重打之前先挪走旧 dist 目录。** PyInstaller 会整目录删除重建，其中
`dist/PDF翻译工具DYNAMIC定制版` 有一千多个文件，会被安全策略拦下来：

```bash
mv "dist/PDF翻译工具DYNAMIC定制版" "dist/_old_dyn"
```

## 跟随通用版修 bug 的流程

1. 通用版改完、验证过，拉到最新代码
2. 判断这个修复是否影响定制版
   - 影响：改 `editions/dynamic.json` 的 version 往上加（1.0.0 → 1.0.1）
   - 不影响：不动，下次攒一起
3. 跑 `python packaging/build_edition.py dynamic`
4. 在 `packaging/release_notes_dynamic_<版本>.md` 写这一版受影响的内容
   - 只写这版相关的，不复述通用版的全部改动
5. 把安装包 + 更新说明发给客户

**什么算影响**：图形/文字排版、单位换算、OCR、符号识别、术语库逻辑、文件读写。
**什么不算**：只影响界面文案、只影响通用版默认配置、只影响英文界面。

判断不了就当作影响 —— 多打一次包的成本远低于客户那边拿到错的图。

## 改配置

`editions/dynamic.json` 各字段：

| 字段 | 作用 | 改之前想清楚 |
|---|---|---|
| `name_zh` / `name_en` | 窗口标题、快捷方式、自检报告 | 改了客户会以为换了软件 |
| `version` | 版本号，同时进 exe 属性和安装包名 | 只增不减 |
| `data_dir` | `%APPDATA%` 下的目录名 | **改了客户就「丢了」全部配置和词表** |
| `exe_name` | exe 文件名 | 改了旧快捷方式会指向不存在的文件 |
| `app_id_guid` | 安装包标识 | **绝不能和通用版相同**，否则装一个顶掉另一个 |
| `glossary` | 专属词库文件名 | 相对 `data/` |
| `fixes` | 专属纠错表文件名 | 留空表示没有 |
| `default_dst` | 首次启动的翻译方向 | 只影响还没有配置的那一次 |
| `industry` / `industry_en` | 提示词里的行业标签 | 中英各一份，别把中文塞进英文提示词 |
| `guide` | 安装包里放哪份说明 | — |

`build_edition.py` 会检查两版之间 `app_id_guid` 与 `data_dir` 是否重复，重复直接拒绝打包。

## 改客户词表

`data/glossary_dynamic.csv`，六列：

```
中文,English,分类,方向,备注,勿用
```

- **方向**：留空＝双向；`z2e`＝只中→英；`e2z`＝只英→中。
  有歧义的词只收单向。例：`托盘=rack` 标 `z2e`，因为英文 rack 在别的图纸里多是货架；
  `底座=feet` 标 `z2e`，因为 feet 也是英尺。
- **勿用**：译文里出现这些词就换回指定译名，多个用 `|` 隔开。
  只写「绝不可能指这个东西」的词。base plate 既可能是底座也可能真是底板，写进去越改越错。

这份表会打进安装包，解包后铺到客户的数据目录，客户可以自己改。

词表的修改不算版本更新，不用重新出包 —— 直接发 CSV 让客户替换。
但如果改的是**随包默认值**，那就要重打包，否则新装的客户拿到的是旧表。

## 版本号为什么另起一条线

通用版 1.1.x，定制版 1.0.x。不共用号码。

通用版修的是所有用户都会遇到的缺陷，迭代快；定制版只在「这个客户的图纸或词表受影响」
时才跟。用同一条号，客户看到 1.1.10 会以为自己少装了好几个版本。

## 发布

**不上 GitHub。** 定制版只做本地打包 + 直接发给客户，不进 release，不发布二进制。

代码本身留在本仓库（与通用版同源），但不打 tag、不推送 release。

## 实测记录

首版（1.0.0，基于通用版 1.1.10）：

- 两版自检均 57 项全过
- 客户三页图纸中→英：标题 `Guardrail Pallet` → `Barricade Rack`，
  正文 `Bottom layer of pallet` → `Bottom layer of the rack`
- exe 启动正常，窗口标题、数据目录、词表铺设均正确
- exe 属性：ProductName / FileVersion 1.0.0.0 / OriginalFilename 均正确
