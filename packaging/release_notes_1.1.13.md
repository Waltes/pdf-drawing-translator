# 1.1.13 —— 通用版不再强制全大写

一条行为改动，影响所有英文译文的观感，所以单独发一版。

## 改了什么

英译方向的译文，**通用版不再强制转成全大写**，改由模型按一般翻译规则输出
（句首大写、专有名词大写、其余小写）。定制版不变，仍按图纸标注惯例全大写。

同一份托盘图纸的对照：

| 原文 | 1.1.12（全大写） | 1.1.13（通用版） |
|---|---|---|
| 地毯托盘俯视图 | `CARPET RACK TOP VIEW` | `Carpet tray top view` |
| 上面宽60mm，下面宽100mm，高度50mm | `TOP WIDTH 60mm, BOTTOM WIDTH 100mm, HEIGHT 50mm` | `Top width 60mm, bottom width 100mm, height 50mm` |
| 焊接几字型挂钩 | `WELDED U-SHAPED HOOK` | `welded U-shaped hook` |
| 90公斤/套 | `90kg/SET` | `90kg/set` |

尺寸、型号、标准号、单位一律不受影响：`M10*70` → `M10×70`，`50*50*2.5mm` →
`50×50×2.5mm`，`PVC`、`DN50`、`Ra3.2`、`4-1/8"` 原样照抄。

## 为什么改

全大写是**机械制图标注**的行业惯例，不是翻译规则。通用版面对的图纸种类远不止
标注这一种：一页产品说明、一段技术要求、一张带英文段落的产品资料，整段大写读
起来全是重音，用户会当成排版事故。

这条规则原本是为定制版那个客户（外贸五金建材，图纸发车间和海外买家）定的，后来
一并作用到通用版上，属于范围放大了。

## 怎么实现

`core/casing.py` 加统一入口 `apply_style()`，内部读 `edition.upper_case()`：

- 定制版（`editions/dynamic.json` 里 `"uppercase": "1"`）：走原有全大写规范，
  含单位小写、客户指定写法，一字未改。
- 通用版（默认关）：原样返回。

散在各处的大小写与「指定译名落笔」也跟同一个开关走：

- `core/translate.py` 两处出口（批量出口、重译旁路）
- `core/dict_engine.py` 词典通道两处

做成统一入口而不是在每个出口写 `if`，是因为译文有四条出口（AI / 词典 / 在线免费
接口 / 重译旁路），逐个加条件必然漏 —— 1.1.12 之前重译那条旁路就漏过大小写和标点。

## 验证

新增 `_std_check.py`：固化在通用版跑，统计「整条被全大写」的条目数并输出逐条译文。
不能用 `_batch.py` 验通用版 —— 它一进来就把 `edition.json` 换成定制版。

| 项目 | 结果 |
|---|---|
| 托盘图纸 29 条译文 | 正常大小写 16 条，整条全大写 1 条（`M10×70 OUTER HEX BOLT`，模型按标注写法给的，不是 casing 改的） |
| 验收件 4 条 | 日期 `Date: November 16, 2026`、`Overall length 2790mm`、`Vertical adjustment 100mm`、`RADIUS 35mm ROUND TUBE` |
| 排版体检 | 越界 0、叠字 0、中文残留 0、未译英文 0、<8pt 0（验收件 1 条竖排缩到 7.07pt，原字 9.2pt） |
| 定制版回归 | 托盘图纸 span 40、未译 1（`Omm` OCR 噪声）、全大写行为不变 |

## 顺带

- `_std_check.py` 新增，给后面验通用版用
- 使用说明加 9.11 节「译文的大小写」，写明本版不干预及与定制版的差别
- `data/_ocr_tmp.png` 是 OCR 渲染的固定临时文件名，进程被强杀会残留，下次启动写
  同一个路径时 `Permission denied`，整个文件跑失败。遇到就删掉它再跑
